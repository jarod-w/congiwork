## 1. 背景与目标

计划 §9 把「浏览器 Computer Use」列为 ★★★★，与桌面 Computer Use 并行，覆盖 SaaS 场景。它填补的是 MCP 覆盖不到的部分：**没有 API、或 API 不开放给个人用户的 Web 系统**（内部 CRM、老旧 ERP、政府/银行网站、没有官方 MCP 的小众 SaaS）。

关键判断：**能用 MCP 就不用浏览器自动化。** 浏览器自动化的稳定性和维护成本天然劣于 API。它是补充手段，不是主路径。这个优先级要写进工具选择逻辑，而不只是写在文档里。

目标：

- **G1** 让「网页上能做的事」成为 AI 可执行的能力，覆盖 MCP 空白区。
- **G2** 登录态问题有可用解法——这是浏览器自动化能否落地的第一道坎。
- **G3** 每一步操作可见、可审批、可中断，与 `P0-08` 保持一致的信任模型。

非目标：

- 不做绕过验证码、反爬对抗、账号批量操作。
- 不做无人值守的定时爬取（Phase 3 再议，且需单独的合规评估）。

## 3. 运行模式（BR-1）

| 模式 | 描述 | 登录态 | 适用 | Phase 2 |
|---|---|---|---|---|
| **A. 托管浏览器** | 服务端 Playwright 实例（容器内） | 需用户在托管浏览器中登录一次并持久化 | 公开站点、用户愿意在托管环境登录的 SaaS | ✅ 主力 |
| **B. Attach 本地浏览器** | 桌面端 CDP 连接用户已开的 Chrome | 天然复用用户登录态 | 内网系统、强风控站点、不愿把凭据交给服务端 | ✅ 桌面端提供 |

两种模式共用同一套动作原语与执行逻辑，差别只在 `BrowserSession` 的建立方式。模式 B 的实现归属 `P0-08` 的 `BrowserAdapter`，本文定义共用层。

选择策略：

```text
需要浏览器操作
   │
   ├── 用户已安装桌面端 且 目标站点在"本地优先"清单 → 模式 B
   ├── 用户已安装桌面端 且 用户偏好本地执行         → 模式 B
   └── 其他                                      → 模式 A
```

「本地优先清单」包括：内网域名、银行/支付类、用户手动标记的站点。

## 4. 登录态（BR-2，最大的落地障碍）

这是浏览器自动化真正的难点，比选择器稳定性更关键。

### 4.1 模式 A 的登录方案

**不要求用户提供密码。** 做法是「交互式登录 + 会话持久化」：

```text
任务需要登录 example.com
   │
   ▼ 服务端启动带持久化 profile 的浏览器实例
   ▼ 通过 WebRTC / VNC-over-WebSocket 把浏览器画面投到用户界面
   ▼ 用户在自己的界面上亲自完成登录（含 2FA）
   ▼ 会话 cookie / storage 加密存入该用户的 profile 卷
   ▼ 后续任务复用该 profile，直到失效
```

要点：

- **密码不经过我们的系统**——用户在投屏的浏览器里直接输入，我们只保存登录后的会话状态。这一点必须在授权说明中讲清楚。
- Profile 卷用信封加密存储（复用 `P0-05` §5 的 Credential Vault 机制），每用户每域名一个卷。
- 会话失效时任务中断，走 `P0-04` §4.3 内联引导用户重新登录。
- 用户可在隐私中心查看「已保存登录状态的网站」并逐个清除。

### 4.2 模式 B 的登录方案

直接复用用户浏览器的现有登录态，无需额外处理。这是模式 B 的最大优势，也是为什么强风控站点应优先走模式 B——从用户自己机器、自己浏览器发起的请求，风控特征与真实使用一致。

## 5. 页面理解与定位（BR-4）

**不用像素/视觉识别作为主路径**，与 `P0-08` §4 的分层原则一致：

| 层 | 手段 | 用于 |
|---|---|---|
| L1 | 可访问性树（Playwright `getByRole` / `getByLabel` / `getByText`） | 主路径，语义稳定，不受样式变化影响 |
| L2 | 结构化选择器（`data-testid`、稳定的 aria 属性） | L1 不足时 |
| L3 | 视觉定位（截图 + 多模态模型指坐标） | 兜底，且需明示 |

页面交给 LLM 的表示形式：**精简后的可访问性树**，不是原始 HTML。

```text
原始页面
   │
   ▼ 提取 accessibility snapshot
   ▼ 剪枝：去掉不可见/装饰性/重复节点
   ▼ 编号：给每个可交互元素分配稳定 ref（如 e12）
   ▼ 截断：超出预算时按视口内优先
   │
   ▼ 给 LLM：
     [e3] link "订单管理"
     [e7] textbox "搜索订单号"
     [e8] button "查询"
     [e12] table "订单列表" (rows=20)
```

LLM 输出 `click(e8)` 而非 CSS 选择器——**引用是系统分配的，不是模型生成的**，这消除了模型幻觉出不存在选择器的整类失败。

Token 控制：单页 accessibility 树预算 4000 tokens，超出时分区域按需展开（提供 `expand(e12)` 原语）。

## 6. 审批与证据（BR-5）

浏览器操作对用户是「看不见的」——不像桌面端能看到鼠标在动。因此证据链更重要：

| 时机 | 做法 |
|---|---|
| 执行前 | 关键步骤（提交表单、点击"确认支付"类按钮）展示页面截图 + 高亮目标元素 + 将填入的值 |
| 执行中 | 每步保留一张截图（缩略图），在时间线中可查看 |
| 执行后 | 结果页截图 + 关键信息提取 |

截图存储：默认保留 7 天，仅用户可见，随任务删除而删除。**截图可能含敏感信息**，因此：不进日志、不进诊断上报、不用于模型训练，且在 `browser:web:automate` 的授权说明中明示会截图。

`irreversible` 判定：提交表单、发送消息、下单、删除——这些在浏览器里没有统一 API 能判断。做法是**基于按钮语义的启发式判定 + 保守默认**：

```text
按钮文案/aria-label 命中不可逆词表（提交/确认/支付/删除/发送/下单/Submit/Confirm/Pay/Delete）
   → risk = irreversible → 强制审批
未命中但会导致页面导航或表单提交
   → risk = write → 首次审批
纯读取/导航
   → risk = read
```

保守默认意味着会有一些不必要的审批。这个代价可以接受——在浏览器里替用户点错一个按钮的后果，远比多问一次严重。

## 7. 权限模型（BR-7）

```yaml
- key: browser:web:automate
  display_name: 替你操作网页
  trust_level: L3
  risk: write
  collects: |
    我会读取你指定网页的内容和结构，按你的要求点击、填写。
    关键步骤会截图，方便你事后核对。
  retention: 操作记录保留 30 天，截图保留 7 天
  degraded_behavior: 你可以自己操作，把结果粘贴给我
```

**按域名细分**：Scope 是总开关，但每个新域名首次操作时单独确认一次：

```text
我需要操作 crm.yourcompany.com
这个网站你之前没让我操作过。
[允许这个网站] [只这一次] [不要]
```

已允许的域名清单在隐私中心可见可撤销。这个粒度是必要的——「允许操作网页」和「允许操作我的网银」显然不是一回事。

## 8. 稳定性与成功率（BR-6）

| 策略 | 做法 |
|---|---|
| 等待 | 一律用 Playwright 的自动等待 + 显式条件等待，**禁止固定 sleep** |
| 选择器 | 只用系统分配的 ref（§5），不接受 LLM 生成的选择器 |
| 重试 | `read` 类可重试 2 次；`write` 重试前必须重新读取页面确认状态；`irreversible` 绝不重试 |
| 页面变化检测 | 每次动作前比对页面 ref 是否仍有效，失效则重新 snapshot |
| 超时 | 单动作 30s，单任务浏览器会话 10min |
| 失败诊断 | 失败时保留：截图、accessibility 树快照、动作序列 |

成功率度量：与 `P0-08` §8 同构，建 golden set（20 个跨 5 类站点的任务），每周回归。目标 ≥ 80%——**低于桌面端的 90%，因为外部网站不可控**，这个差异要在产品文案中体现（「网页操作有时会不太顺利」），而不是承诺同等可靠性。

## 9. 合规边界（BR-8）

| 约束 | 说明 |
|---|---|
| 尊重 robots.txt | 对公开站点的批量读取遵守；用户自己账号内的操作不受此限（那是用户自己的数据） |
| 不规避反自动化 | 不做验证码破解、不伪造指纹、不做 IP 轮换。遇到验证码 → 转人工，投屏给用户自己过 |
| 频率限制 | 单域名默认 ≤ 1 req/s，模拟人类节奏 |
| ToS 提示 | 首次操作某域名时，若属已知禁止自动化的站点（维护一个清单），明确提示用户风险 |
| 不做账号批量操作 | 单用户单账号，不支持多账号轮换 |

这些不只是合规姿态——绕过反自动化的方案本身就不稳定，会持续消耗维护成本，且一旦被目标站点封禁会直接损害用户。技术上和商业上都不划算。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 登录态问题导致功能实际不可用 | 极高 | §4 两套方案；模式 B 作为强风控场景的兜底；**M1 先验证登录方案，再投入其余** |
| 操作错误造成用户损失（点错按钮、填错金额） | 极高 | 保守的 irreversible 判定；执行前截图预览；金额/数量类字段强制审批 |
| 网站改版导致大面积失效 | 中 | 语义定位（L1）比 CSS 选择器抗改版；失败诊断保留证据便于快速修 |
| 截图泄露敏感信息 | 高 | 不进日志/诊断；7 天过期；随任务删除；授权说明明示 |
| 被目标站点封禁账号 | 高 | §9 的频率与不规避约束；已知禁止自动化的站点提前警示 |
| 与 MCP 能力重复建设 | 中 | 工具选择逻辑中 MCP 优先级高于浏览器；同一 SaaS 有 MCP 连接器时不暴露浏览器路径 |

## 11. 验收标准

1. golden set 成功率 ≥ 80%（5 类站点各 4 个任务）。
2. 登录流程端到端可用：用户在投屏中完成含 2FA 的登录，后续任务复用会话。
3. 密码不出现在服务端任何存储、日志、trace 中（扫描验证）。
4. 不可逆按钮的启发式判定：构造 20 个真实页面样本，召回率 ≥ 95%（宁可误报）。
5. 新域名首次操作触发单独确认（自动化测试）。
6. 遇到验证码时不尝试破解，正确转为人工接管。
7. 同一 SaaS 同时有 MCP 连接器与浏览器路径时，Runtime 选择 MCP（自动化测试）。

## 13. 待决问题

1. 投屏方案的技术选型（WebRTC vs noVNC）需要在 M1 验证延迟与体验，尤其是移动网络下。
2. 托管浏览器的资源成本：每个活跃会话一个容器，成本不低。是否需要会话池 + 空闲回收？建议 M3 时按实际并发量决定，Phase 2 初期可先用简单的按需启停。
3. 「已知禁止自动化的站点清单」如何维护？倾向只维护少量高风险类别（银行、支付、政务），不做全面清单。
