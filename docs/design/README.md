## 建议交付顺序（Phase 1）

| 序 | 内容 | 说明 |
|---|---|---|
| 0 | **P0-07 M0：前置用户实验** | 计划 §2.1 要求的 5–10 人授权意愿验证。**结论影响后续全部投入规模，必须最先做** |
| 0 | **P0-05 M0：提交 Google 应用验证 + CASA** | **阻塞性已恢复并升级**（2026-08-18 改定，推翻 B3 / A7）。首批含 Gmail + Calendar 两个 Google 连接器，`gmail.*` 属 restricted scope，需第三方安全评估。**周期不由我们控制，必须立项第 1 周提交**。配套 G1/G2 检查点与「只发不读」降级预案，见 `P0-05` §2.1.1 |
| 0 | **P0-08 D0：桌面 L1 接口预研** | 决定首批适配哪些应用，Go/No-Go 检查点 |
| 1 | P0-07 + P0-03 底座 | Consent 与 Runtime，其余模块都依赖 |
| 2 | P0-02 Memory + P0-04 工作台 | 打通"能派活、有记忆"的主循环 |
| 3 | P0-01 画像 + P0-05 只读连接器 | 信任爬坡 L1→L2。首批连接器 = **Gmail + Google Calendar + Notion + GitHub（4 个）**。**M3 按「Calendar + Notion 先做、Gmail 最后做」拆**，使 CASA 的不确定性只影响里程碑尾部 |
| 4 | P0-06 Skill + P0-05 写能力 | 信任爬坡 L3（SaaS 侧）。GitHub 在此承担审批链路的验证载体角色——**它不依赖任何外部审核，这正是不能用 Gmail 替代它的原因**（用 Gmail 当验证载体等于把审批链路验证也压在 CASA 上） |
| 5 | P0-08 桌面 Computer Use | **独立子团队/独立里程碑**（计划 §231），双平台 **107 人日**（B5 只做 Graph 后从 113 降下来），含 15d 专用缓冲 |

三个「序 0」项都是前置阻塞项，晚启动会在中后期造成排期塌方。其中：

- **前置用户实验**的招募口径已定为「海外市场 / 运营岗、非熟人」，招募难度高于国内同岗位，**招募必须与设计并行启动而非串行**（见 `P0-07` §11）。
- **P0-05 M0** 是三项里唯一**产出时间完全不由我们决定**的——加人加班都压不动 Google 的评估队列。它自身只占 3 人日，却定义了关键路径的形状。

**排期前提（已按 A 组结论重算并定案）**：

| 项 | 值 |
|---|---|
| 需求量 | 约 **302 人日**（原记 255。P0-08 因 A4 双平台 78→113、**再因 B5 只做 Graph −6 至 107**；P0-03 因 A6 custom provider +5；P0-05 因 2026-08-18 连接器改定 27→32） |
| 团队 | **5 人**（A5），其中 1–2 人专做 P0-08 |
| 周期 | **3.5 个月**（A9 定案，原 3 个月不够）≈ 76 工作日/人 |
| 有效容量 | 约 **304 人日**（按 20% 协作损耗）/ 约 **285 人日**（按 25%） |
| 范围 | **不砍**（A10 确认）——三个适配器 × 双平台、四个连接器、访谈三轮、Skill 嵌套 1 层全做。桌面邮件按 B5 只做 Graph API 一条路径 |

⚠️ **余量约 2 人日，等同于没有余量**：2026-08-18 当天两次相反方向的调整基本相抵——连接器改定 **+5d**、B5「桌面邮件只做 Graph」**−6d**，净 −1d。20% 损耗下余量约 2 人日，**25% 损耗下仍缺约 17 人日**。数字看起来打平了，但这不构成放松的理由。配套三条硬要求（详见 [P0-open-questions.md](P0-open-questions.md) §1.2 A9.1 与 **A10**）：

1. **容量复核提前到第 3 周末**，与 `P0-05` §2.1.1 的 G1 检查点合并成一次会。A9.1 原定的第 1 个月末复核保留，变成第二次。提前的理由：改定后前期不确定性显著上升，第 1 个月末才看第一眼太晚。
2. **预案第一刀是「macOS 侧只上 Excel」**（省 18d）。门禁已是（适配器 × 平台）矩阵粒度，这么砍不需要改任何设计——但**必须在前期砍，不能拖到第三个月末**，否则已投入的 macOS 适配工作全废。后续两刀：B8 Skill 嵌套不做（3d）、`P0-01` 访谈缩到 2 轮（3d），合计 24d，足以覆盖保守假设下的 23 人日缺口。
3. **但这 5 人日不是真正的问题**。真正变了的是风险性质——排期上现在压着一个**外部不可控项**（Google CASA 评估周期），它无法靠加人或加班压缩，最坏情况是 Gmail 整个不能上线。对策是把它从关键路径上挪下来（M3 拆序 + G1/G2 检查点 + 降级预案），而不是去别处找 5 人日。**其中一个问题需要决策者明确表态：Phase 1 退出条件是否允许在 Gmail 未上线的情况下达成**——按下方三条退出条件的字面表述答案是「允许」，但这是从文字推出来的，不是有人拍过板的。见 A10。

## Phase 1 退出条件（来自规划 §6）

数值已按 `P0-open-questions.md` A3 / A4 确认：

| 条件 | 判定口径 | 支撑文档 |
|---|---|---|
| **≥ 6** 个真实用户进入信任爬坡第三层 | 授权了 L3 Scope **且此后有过成功执行**；只授权不用不计入 | `P0-04` §9 埋点口径、`P0-07` §11 |
| 用户自发创建 ≥ 3 个手动 Skill 并复用 | `source ∈ {manual, from_task}`，**复制预置示例（`preset_copy`）不计入** | `P0-06` §5.5 / §9、`P0-04` §9 |
| 桌面 Computer Use 成功率 ≥ 90% | 按 **（适配器 × 平台）** 逐组合判定，不做跨平台平均；达标的组合上线，未达标的不上线并在客户端明示 | `P0-08` §8.1 / §8.3 |

N = 6 样本很小，前两条的判定必须结合 `P0-07` §11 的定性访谈，不能只看数字。

**这三条都不点名任何具体连接器**——「进入 L3」可以通过 `tool:notion:write`、`tool:github:write`、`desktop:excel:automate` 中任一达成。**A10 已确认（2026-08-18）：Phase 1 退出条件允许 Gmail 未上线就达成。** 因此 Google CASA 审核从产品级阻塞降为功能风险，`P0-05` §2.1.1 的「只发不读」降级预案是被认可的终态路径，而不是应急措施。

⚠️ **但「退出条件不要求」不等于「用户不需要」。** A10 与 B5 叠加后有一个盲区：CASA 未过时，**Gmail 用户的邮件能力只剩粘贴**——桌面 MailAdapter 按 B5 只做 Graph API，而 Graph 覆盖 M365 用户，与 Gmail 用户不重叠，两条路互相兜不了底。已配触发式补做（G2 未过 + 实验显示 Gmail 占比高 → 补 Outlook COM，3d，见 `P0-08` §2.1）。**这个盲区的实际规模取决于前置实验的邮箱分布数据**，那道题因此从「排序参考」升为「触发判据」。

## 相对规划的设计偏离（需评审确认）

设计过程中有若干处偏离或细化了原规划，集中列出以便评审：

| 编号 | 出处 | 规划原文 | 设计调整 | 理由 |
|---|---|---|---|---|
| 1 | §4.4 §7.2 | 桌面自动化用「PyAutoGUI / Accessibility API」 | 改为**分层降级**：L1 原生 API（COM/AppleScript/CDP/Graph）优先，Accessibility 次之，PyAutoGUI 仅兜底；L3 使用率 >10% 视为适配不合格 | 规划 §2.3 已预警 UI 自动化脆弱，而 §6 要求 ≥90% 成功率，纯 UI 路径难以同时满足。详见 `P0-08` §4 |
| 2 | §4.5 | 「只记录应用内的结构化操作事件」 | 进一步收窄为**只采集 CogniWork 参与的操作**，不采集用户独立完成的操作 | 常驻监听会滑向监控软件，与 §2.1 自愿模型不相容。代价是覆盖面变窄，属刻意取舍。详见 `P1-01` §3 |
| 3 | §7.9 | Skill 含 `success_rate` 字段 | 改为由 `success_count / run_count` 派生 | 避免存储可推导值导致不一致 |
| 4 | §3 | Skill Engine 整体标为 P1 | 拆分：**手动创建/执行归 P0**（`P0-06`），演进能力归 P1（`P1-03`） | §4.3 已把手动 Skill 创建列入 P0，且它是 Phase 1 退出条件之一 |
| 5 | — | 规划未涉及 | 新增 `P1-04` 浏览器自动化中的**登录态方案**（投屏交互式登录 + 会话持久化，密码不经服务端） | 登录态是浏览器自动化最大的落地障碍，需在设计阶段定方案 |
| 6 | §2.1 | 「写进设计评审的检查项」 | 落为三层机制：PR 模板 + CI 自动守护 + **零授权 E2E 测试** | 把声明变成可执行约束。详见 `P0-07` §8 |
| 7 | §7.10 | 「优先支持浏览器可达的 SaaS（**Slack**、Notion、Gmail、GitHub）」 | **首批 = Gmail + Google Calendar + Notion + GitHub（4 个）**。相对原文两处偏离：**Slack 移出**（原文有，转入 `P0-05` §2.2 候选池）、**Google Calendar 加入**（原文无）。Gmail 回到原文之内 | 决策者 2026-08-18 改定，推翻此前的 B3（Gmail 移出）与 A7（Calendar 移出）。理由：邮件是 A1 三类高频任务之一，上一版把它整个推给桌面端，代价是 **Web 端用户完全没有邮件能力**；Calendar 与 Gmail 共用同一套 Google 接入与验证材料，边际成本低。**代价是 Google CASA 审核回到关键路径**——配套 G1/G2 检查点与「只发不读」降级预案。详见 `P0-05` §2.1 / §2.1.1、`P0-open-questions.md` A10 |
| 8 | §7.6 | 「先支持 1-2 家跑通」（未提及自定义供应商） | 2 家内置（Anthropic + OpenAI）**外加「用户自定义 provider」能力**——规划未涉及的新增范围 | A6 决策。代价是引入两个必须处理的问题：`base_url` 的 SSRF 防护、tool-use 能力探测与不降级；新增 Scope `llm:custom:route` 与约 4 人日。详见 `P0-03` §7.1 |
| 9 | §6 | 「桌面 Computer Use 白名单应用操作成功率 ≥ 90%」 | 判定粒度细化为 **（适配器 × 平台）逐组合**，不做跨平台平均；未达标组合不上线且在客户端明示 | A4 选双平台后，合并统计会把 Windows 96% 与 macOS 82% 平均成「达标」，掩盖 macOS 的真实质量。详见 `P0-08` §8.3 |
| 10 | §7.7 | 「PostgreSQL + pgvector 一套存储」 | Phase 1 实现仍是**一套 PostgreSQL、不引入独立向量库**。embedding 列用 `real[]`，余弦在应用层。原因：CI 与官方 `postgres:16` 镜像没有 `vector` 扩展。生产若装 pgvector，后续迁移可改 `vector(1024)` + HNSW，接口不用动 | 硬约束「一套存储」保留；把「必须现在装扩展」从阻塞项拿掉。详见 `apps/backend/migrations/0004_memory.sql` |
| 11 | `P0-05` §3 / §3.1 | 架构图含 **streamable-http server**（远端托管连接器），标注「✅ 支持接入，按需」 | Phase 1 **不实现** streamable-http 传输。`mcp_transport` 只有 `stdio`（生产默认）与 `inprocess`（单测），填其它值启动即报错，不静默回落 | Phase 1 四个连接器全是自托管 stdio，没有消费方。按 §3.1 的「按需」延后。登记在这里而不是留在代码里，是因为「支持接入」这句话在文档里读起来像已经有了 —— 认了一个不存在的能力比没有这个能力更糟。详见 `apps/backend/src/cogniwork/tools/mcp.py` |
| 12 | `P0-05` §3.1 | 「自托管连接器统一放在 `packages/mcp-connectors`，每个连接器是一个独立的 MCP server 实现」 | 实现放在 `apps/backend/src/cogniwork/tools/`（`mcp.py` / `providers.py` / `mcp_server.py`），`packages/mcp-connectors` 只留说明。stdio 入口是 `python -m cogniwork.tools.mcp_server --provider <id>`，**进程隔离要求不受影响** | 四个适配器共用 Vault、catalog、HttpTransport 与错误模型。拆成独立包会把这些复制一遍或引一条反向依赖，而 Phase 1 没有「连接器独立发版」的需求。`P0-08` 的桌面 Agent 才是真需要独立版本节奏的那个，它在独立仓库 |
| 13 | `P0-02` §12 待决 1 | 「中文全文检索是否投入分词，建议先跑评测用数据决定」 | **Phase 1 不投入。** 中文查询的 lexical 分量恒为 0（连子串都不得分），检索完全依赖向量召回；有一条测试把这个测量钉住（`test_memory_eval.py`） | A2 目标市场是海外英语市场，中文检索质量不影响退出条件。代价一侧：`pg_jieba` 是 PG 扩展，官方 `postgres:16` 没有，引入会把 CI 与生产镜像绑到自定义构建 —— 与偏离 10 同一条理由。Phase 2 若开放中文市场，先评估**应用层分词**（或 CJK 字符 bigram，不需要词典），不引入 PG 扩展。详见 `docs/eval/memory-retrieval.md` |
