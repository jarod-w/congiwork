## 建议交付顺序（Phase 1）

| 序 | 内容 | 说明 |
|---|---|---|
| 0 | **P0-07 M0：前置用户实验** | 计划 §2.1 要求的 5–10 人授权意愿验证。**结论影响后续全部投入规模，必须最先做** |
| 0 | **P0-05 M0：提交 OAuth 应用审核** | Google/Slack 审核周期以周计，是隐性阻塞项，与上一项并行启动 |
| 0 | **P0-08 D0：桌面 L1 接口预研** | 决定首批适配哪些应用，Go/No-Go 检查点 |
| 1 | P0-07 + P0-03 底座 | Consent 与 Runtime，其余模块都依赖 |
| 2 | P0-02 Memory + P0-04 工作台 | 打通"能派活、有记忆"的主循环 |
| 3 | P0-01 画像 + P0-05 只读连接器 | 信任爬坡 L1→L2 |
| 4 | P0-06 Skill + P0-05 写能力 | 信任爬坡 L3（SaaS 侧） |
| 5 | P0-08 桌面 Computer Use | **独立子团队/独立里程碑**（计划 §231），含 10d 专用缓冲 |

三个「序 0」项都是前置阻塞项，晚启动会在中后期造成排期塌方。

## 相对规划的设计偏离（需评审确认）

设计过程中有若干处偏离或细化了原规划，集中列出以便评审：

| 编号 | 出处 | 规划原文 | 设计调整 | 理由 |
|---|---|---|---|---|
| 1 | §4.4 §7.2 | 桌面自动化用「PyAutoGUI / Accessibility API」 | 改为**分层降级**：L1 原生 API（COM/AppleScript/CDP/Graph）优先，Accessibility 次之，PyAutoGUI 仅兜底；L3 使用率 >10% 视为适配不合格 | 规划 §2.3 已预警 UI 自动化脆弱，而 §6 要求 ≥90% 成功率，纯 UI 路径难以同时满足。详见 `P0-08` §4 |
| 2 | §4.5 | 「只记录应用内的结构化操作事件」 | 进一步收窄为**只采集 CogniWork 参与的操作**，不采集用户独立完成的操作 | 常驻监听会滑向监控软件，与 §2.1 自愿模型不相容。代价是覆盖面变窄，属刻意取舍。详见 `P1-01` §3 |
| 3 | §7.9 | Skill 含 `success_rate` 字段 | 改为由 `success_count / run_count` 派生 | 避免存储可推导值导致不一致 |
| 4 | §3 | Skill Engine 整体标为 P1 | 拆分：**手动创建/执行归 P0**（`P0-06`），演进能力归 P1（`P1-03`） | §4.3 已把手动 Skill 创建列入 P0，且它是 Phase 1 退出条件之一 |
| 5 | — | 规划未涉及 | 新增 `P1-04` 浏览器自动化中的**登录态方案**（投屏交互式登录 + 会话持久化，密码不经服务端） | 登录态是浏览器自动化最大的落地障碍，需在设计阶段定方案 |
| 6 | §2.1 | 「写进设计评审的检查项」 | 落为三层机制：PR 模板 + CI 自动守护 + **零授权 E2E 测试** | 把声明变成可执行约束。详见 `P0-07` §8 |
