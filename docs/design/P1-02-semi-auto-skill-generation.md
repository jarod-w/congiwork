## 1. 背景与目标

计划 §2.2 对这一块给了明确的风险判断和对策：全自动工作流挖掘「3-6 个月做出稳定可用的版本偏乐观」，因此**先做「人工标注 + AI 辅助总结」的半自动路径**，全自动作为 Phase 2 的探索方向、不作为承诺交付物。

计划 §4.6 给的流程是：

```text
用户手动标记"这是一个可重复流程" → AI 整理该流程的操作历史
→ 生成结构化 Skill 草稿 → 用户确认/修改 → 纳入 Skill 库
```

本文设计这条路径。核心判断：**这个模块的难点不在"生成"，在"参数化"和"边界判定"** ——把一次具体执行泛化成可复用流程，需要知道哪些值下次会变、哪些步骤是偶然的。

目标：

- **G1** 用户标记后，生成的 Skill 草稿可用度足够高——用户修改量 ≤ 30%（否则不如自己写）。
- **G2** 参数化候选的准确率足以让用户「点选确认」而非「重新填写」。
- **G3** 生成的 Skill 与手动创建的 Skill **结构完全一致**（`P0-06` §4），下游无差别。

非目标：

- 不做无标记的自动模式发现（`P1-06`）。
- 不做跨用户的 Skill 模式学习（Phase 3）。

---

## 2. 与 P0-06「从任务创建」的关系

`P0-06` §5.2 已经实现了一条简化路径：单个任务 → Skill 草稿。本模块是它的增强，增加三件事：

| 能力 | P0-06 | P1-02 |
|---|---|---|
| 输入 | 单个 task 的 step 序列 | **跨任务的事件序列**（多次执行同一流程） |
| 参数化 | AI 给候选，用户逐个确认 | **多次执行的差异分析**自动识别变量 |
| 步骤泛化 | 直接映射 step | 合并/剔除偶然步骤，识别可选分支 |
| 触发条件 | 用户手填 | 从执行的时间/上下文模式中建议 |

**多次执行的差异分析是本模块的核心价值**：一次执行看不出哪个值是变量，三次执行一比对，变的就是变量，不变的就是常量。这比让 LLM 猜可靠得多。

| 编号 | 需求点 | 描述 | 验收 |
|---|---|---|---|
| SG-1 | 流程标记 | 用户在时间线上圈选一段，或对某任务标记「这是我常做的」 | ≤3 次点击 |

## 4. 数据来源

三个来源，按可得性排序：

| 来源 | 结构化程度 | 需要授权 | 覆盖 |
|---|---|---|---|
| `task_step` 序列（`P0-03`） | 高 | 无（系统自身记录） | AI 执行过的全部流程 |
| `activity_event`（`P1-01`） | 高 | `telemetry:*:collect` | 桌面/浏览器细粒度动作 |
| `episodic_record.user_edits`（`P0-02`） | 中 | 无 | 用户的修正行为 → 偏好与约束 |

**重要**：`task_step` 是零授权可得的。这意味着**即使 `P1-01` 的授权率不理想，本模块仍然可以工作**——只是粒度粗一些。这是有意的解耦设计，避免本模块的成败被 L4 授权率绑架。

## 5. 关键流程

### 5.1 相似执行聚合（SG-2）

```text
用户标记的 task T
   │
   ▼ 候选召回（近 90 天内）：
   │    · 同 skill_id（若 T 由 Skill 执行）→ 直接命中
   │    · 同 intent 标签
   │    · task 描述的向量相似度 > 0.8
   │    · 工具序列的编辑距离 < 阈值
   │
   ▼ LLM 判定："这些是同一个流程的不同次执行吗？"（逐个二分类）
   │
   ▼ 聚类结果 → 展示给用户："我找到你做过 4 次类似的事，一起分析？"
   │    用户可勾掉不属于同一流程的
   ▼ 确认后的执行集合 E = {e1, e2, ..., en}
```

用户可勾选剔除是必要的：聚类错误会污染后续的差异分析，而用户一眼就能看出哪次不是同一件事。

`n = 1` 时退化为 `P0-06` §5.2 的单次路径；`n ≥ 3` 时差异分析才真正有效。

### 5.2 序列规范化（SG-3）

对每个执行 `ei`，把 step/event 序列清洗为规范序列：

| 操作 | 规则 |
|---|---|
| 剔除失败重试 | 同一 action 连续失败后成功，只保留成功那次 |
| 剔除澄清往返 | `builtin.ask_user` + 用户回答 → 折叠为一个 `collect_input` 步骤 |
| 合并连续 llm 步骤 | 相邻的纯推理步骤合并，除非中间有工具调用 |
| 剔除探索性读取 | 只读且结果未被后续步骤使用的调用（用数据流分析判定） |
| 统一动作命名 | 映射到 `ActionSpec` 的规范名 |

「剔除探索性读取」值得说明：AI 在执行时常常先读一堆东西再决定做什么，这些探索步骤不属于流程本身。判定方法是简单的数据流分析——该步骤的输出是否出现在后续步骤的输入中（用 digest 的 key 关联，不需要精确追踪）。

### 5.3 差异化参数抽取（SG-4，核心）

```text
规范化后的 n 个序列
   │
   ▼ ① 序列对齐（多序列比对，类似 diff 的 LCS 扩展）
   │     输出：公共步骤骨架 + 每个位置的变体
   │
   ▼ ② 逐步骤逐参数比对
   │     · 所有执行中值相同 → 常量
   │     · 值不同但类型一致 → 【变量候选】
   │     · 值不同且类型不同 → 步骤可能不同，标记为分支候选
   │
   ▼ ③ 变量语义命名（LLM）
   │     值集合 {"2025Q1","2025Q2","2025Q3"} → 参数名 quarter，类型 enum/string
   │     值集合 {"周报-0801.xlsx","周报-0808.xlsx"} → 参数名 source_file，类型 file
   │
   ▼ ④ 派生关系识别（LLM，尽力而为）
   │     若某参数总是等于"当前日期所在季度"，标记为可自动填充
   │
   ▼ 参数清单 + 骨架 workflow
```

第 ① 步的序列对齐用经典算法而非 LLM——多序列比对是确定性问题，用 LLM 又慢又不稳。LLM 只用在第 ③④ 步的语义命名上，那才是它擅长的。

**这是本模块最重要的实现原则：结构分析用算法，语义理解用 LLM。** 计划 §2.2 判断全自动挖掘偏乐观，很大程度上是因为业界常见做法是把整件事丢给 LLM。把确定性部分交回算法，可行性会好很多。

### 5.4 草稿生成与确认（SG-5/SG-6）

生成的草稿呈现给用户时，**要展示证据**：

```text
技能草稿：季度渠道复盘

参数（我从你的 4 次执行中发现的）
  · 季度        你每次都不一样：2025Q1 / Q2 / Q3 / Q4    ✓ 确认是参数
  · 渠道范围     你每次都是"全部"                        ○ 设为固定值 ● 改成参数
  · 输出频道     你每次都是 #marketing                   ○ 设为固定值 ● 改成参数

步骤（4 次执行中的共同部分）
  1. 从 HubSpot 拉取数据            4/4 次都做了
  2. 按渠道汇总找出变化最大的三个     4/4 次都做了
  3. 加一段环比原因分析              2/4 次做了   ← [保留为可选步骤] [删除]
  4. 发到 Slack                    4/4 次都做了

                            [试运行] [保存为技能]
```

「4/4 次都做了」这类证据展示是关键——它让用户能判断 AI 的归纳对不对，而不是盲目接受。只做了 2/4 次的步骤明确标出来让用户裁决，而不是 AI 替他决定。

### 5.5 主动建议（SG-7）

检测规则（保守，宁可少提示）：

```text
同一 intent 的任务在 14 天内出现 ≥3 次
  且 尚无对应 Skill
  且 该用户近 30 天未拒绝过同类建议
      → 在任务结果卡片中追加一条建议（不弹窗、不打断）
```

用户拒绝后 30 天内不再对该 intent 提示。连续拒绝 3 次则关闭该用户的主动建议功能，并在设置中留开关。

## 6. 技术方案

| 环节 | 方案 | 说明 |
|---|---|---|
| 相似召回 | pgvector（复用 `P0-02` 基础设施） | 不引入新组件 |
| 序列对齐 | 多序列比对（渐进式对齐，以最长序列为参考） | 纯算法，Python 实现 |
| 参数类型推断 | 规则（日期/数字/枚举/文件/URL/邮箱）+ LLM 兜底 | 规则优先，快且稳 |
| 语义命名 | 结构化输出 LLM 调用，单次批量处理全部参数 | 控成本 |
| 草稿校验 | JSON Schema 校验 + 工具存在性校验 + Scope 推导校验 | 不通过不允许保存 |

**离线批处理而非实时**：聚合与分析在用户点击「分析」后异步执行（预计 10–30 秒），进度用 SSE 推送。不做后台常驻计算。

## 7. 验收标准

| 项 | 标准 | 测量方法 |
|---|---|---|
| 参数抽取准确率 | ≥ 70% | 人工标注 30 个真实流程的正确参数集，比对 F1 |
| 步骤召回率 | ≥ 85% | 生成的 workflow 覆盖人工认定的必要步骤比例 |
| 用户修改量 | ≤ 30% | 保存时的 diff 行数 / 草稿总行数，取中位数 |
| 生成后首次执行成功率 | ≥ 70% | 生成的 Skill 第一次真实运行的成功比例 |
| 结构合法性 | 100% | 全部草稿通过 `P0-06` schema 校验 |
| 主动建议接受率 | ≥ 25% | 低于此值说明打扰大于价值，需调高触发门槛 |

评测集：从 Phase 1 真实用户数据中抽取 30 个多次执行的流程，人工标注 ground truth，作为固定回归集，结果记入 `docs/eval/skill-generation.md`。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 用户根本不标记（不知道该标什么） | 高 | SG-7 主动建议是主入口，用户标记是辅助；建议时用具体的话术「你这个月做了 4 次季度复盘，要存成技能吗」 |
| 单次执行样本（n=1）居多，差异分析失效 | 中 | n=1 时明确降级为 `P0-06` 路径并告知用户「多做几次后我能总结得更好」，把这变成正反馈而非缺陷 |
| 参数化错误导致 Skill 复用时出错 | 高 | 证据展示（§5.4）让用户可判断；强制引导试运行；首次执行失败后主动提示修正 |
| LLM 归纳出用户并不认可的流程 | 中 | 所有归纳都附证据（n/m 次）；可选步骤交用户裁决而非默认保留 |
| 依赖 `P1-01` 授权率 | 中 | §4 的解耦设计：`task_step` 零授权可得，本模块不硬依赖 `P1-01` |
| 主动建议变成骚扰 | 中 | 保守触发规则；拒绝即长期静默；提供总开关 |

## 10. 待决问题

1. 参数抽取 70% 的准确率目标是否够用？低于这个值用户会觉得「还不如自己填」。建议 M1 建好评测集后先跑一版 baseline，用实际数据校准目标。
2. 是否支持从 Skill 的多次执行中「反向优化 Skill」（发现用户每次都改同一个地方 → 建议更新 Skill）？这属于 `P1-03` 的范围，但数据管线在本模块，需确定归属。
