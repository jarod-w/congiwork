## 0. 本文性质说明

计划对这一项的表述非常明确：

- §2.2：「从行为日志中自动发现『可复用工作流』并生成可靠 Skill，目前业界都还处于早期阶段，3-6 个月做出稳定可用的版本偏乐观」
- §4.6：「全自动 Workflow Mining 作为探索方向，**视 Phase 2 中期的技术验证结果决定是否投入**」
- §6：「探索：自动发现重复模式（**不承诺**，作为研究方向）」

因此本文不是实现设计，而是**一份研究计划**：定义要回答的问题、怎么验证、以及什么条件下应该放弃。它的主要价值是防止两件事——为了"看起来先进"而提前投入，以及在没有判据的情况下无限期投入。

---

## 1. 要回答的核心问题

> 在不要求用户标记的前提下，能否从操作日志中自动发现**用户认可**的可复用流程？

拆成三个可验证的子问题：

| 编号 | 问题 | 为什么难 |
|---|---|---|
| Q1 | 能否可靠地把连续的操作流切分成「一件事」？ | 用户的工作是交错的，边界模糊 |
| Q2 | 能否识别出"同一件事"的多次执行？ | 表面参数不同，步骤可能有增减 |
| Q3 | 发现的模式，用户认为值得沉淀成 Skill 吗？ | **这是真正的判据**——技术上发现了但用户觉得没用，等于没发现 |

Q3 是最容易被忽略、也最关键的一个。业界很多工作流挖掘的成果卡在这里：算法上"发现"了大量重复模式，但绝大多数是琐碎的、不值得自动化的。

---

## 2. 数据前提（先检查是否具备）

| 前提 | 来源 | 检查方法 |
|---|---|---|
| 有足够的事件量 | `P1-01` | 单用户日均 ≥ 50 条结构化事件，且有 ≥ 30 名这样的用户 |
| 事件有足够语义 | `P1-01` §4 | `input_digest.summary` 可用于语义聚类 |
| 有 ground truth | `P1-02` | 用户手动/半自动创建的 Skill 就是"用户认可的流程"的标注 |

**`P1-02` 产出的 Skill 是本研究最宝贵的资产**——它天然是「用户认为值得沉淀的流程」的标注集。若 `P1-02` 累计产出的 Skill 少于 100 个，本研究缺乏评估基准，不应启动。

**数据前提不满足 → 不启动研究。** 这是第一道门。

## 3. 方法路线（三条，按投入递增）

### 路线 A：规则 + 序列挖掘（基线）

```text
事件流
  ▼ 会话切分：15 分钟静默 / 应用切换 / 任务边界
  ▼ 频繁序列挖掘（PrefixSpan 或 SPADE）
  ▼ 过滤：支持度 ≥ 3、长度 ≥ 3、非平凡（排除单一动作重复）
  ▼ 候选模式
```

优点：确定性、可解释、成本近乎为零、可先跑起来看看数据长什么样。
缺点：只能发现字面重复，对参数变化和步骤增减不敏感。

**建议先做 A**，它的主要作用是回答「数据里到底有没有重复模式」这个前置问题。如果连 A 都挖不出东西，后面两条路线也不必谈。

### 路线 B：语义嵌入 + 聚类

```text
事件流
  ▼ 会话切分（同 A）
  ▼ 会话级语义表示：事件 summary 序列 → 嵌入
  ▼ 聚类（HDBSCAN，不预设簇数）
  ▼ 簇内序列对齐（复用 P1-02 §5.3 的算法）
  ▼ 候选模式 + 参数
```

优点：能识别"做的是同一件事但细节不同"。
缺点：聚类质量难调；簇的语义边界与用户心智不一定对齐。

### 路线 C：LLM 直接归纳

```text
一段时间窗内的事件流 → LLM → "你这周重复做了这几件事"
```

优点：语义理解强，能给出人话描述。
缺点：成本高（长序列）、不可复现、容易产生看似合理实则无用的归纳。

**建议 C 只用作 A/B 结果的语义命名与描述生成层，而不是作为发现主体。** 这与 `P1-02` §5.3 的原则一致：结构分析用算法，语义理解用 LLM。

## 4. 评估方法

### 4.1 离线评估

用 `P1-02` 已产出的 Skill 作为标注集，做"能否重新发现"测试：

```text
取用户 U 手动创建的 Skill S（对应 n 次历史执行）
  ▼ 把这 n 次执行的事件混入 U 的全部事件流
  ▼ 跑挖掘算法（算法不知道 S 存在）
  ▼ 看是否召回了 S 对应的模式
```

指标：

| 指标 | 定义 | 目标 |
|---|---|---|
| 模式召回率 | 已知 Skill 被重新发现的比例 | ≥ 60% |
| 模式精确率 | 挖出的模式中，人工判定"值得沉淀"的比例 | ≥ 30% |
| 噪声率 | 平凡/琐碎模式占比 | ≤ 40% |

### 4.2 在线评估（决定性判据）

离线指标再好，也不等于用户要。真正的判据是：

| 指标 | 定义 | Go 阈值 |
|---|---|---|
| **建议采纳率** | 自动发现的流程建议中，用户点击"存为技能"的比例 | **≥ 20%** |
| 建议后 Skill 复用率 | 由自动建议产生的 Skill，后续被真实复用的比例 | ≥ 50% |
| 打扰负反馈率 | 用户点"别再建议了"的比例 | ≤ 15% |

在线评估方式：把自动发现的建议**混入 `P1-02` 的主动建议渠道**（`P1-02` §5.5），用同样的 UI 呈现，对比两个来源的采纳率。这样不需要新建界面，且有天然对照组。

## 5. Go / No-Go 决策门

分三个检查点，每个都可以终止：

| 检查点 | 时机 | Go 条件 | No-Go 处置 |
|---|---|---|---|
| **G0 数据门** | 研究启动前 | §2 数据前提全部满足 | 不启动，等数据积累；重新评估 `P1-01` 授权率 |
| **G1 可行性门** | 路线 A 跑通后（约 2 周） | 离线模式召回率 ≥ 40%，且人工抽检认为模式有意义 | **终止**，结论回写规划：全自动路径在当前数据条件下不可行 |
| **G2 价值门** | 在线小流量 4 周后 | 建议采纳率 ≥ 20% 且负反馈率 ≤ 15% | **终止**，保留半自动路径（`P1-02`）为唯一方案 |

**No-Go 不是失败。** 计划 §2.2 已经预判了这条路径偏乐观，及早得出否定结论、把资源投回半自动路径，本身就是这项研究的有效产出。研究结论无论正负，都要写成文档回写到规划中，避免同一个问题在 Phase 3 被重新提出并重新投入。

## 6. 投入约束

| 项 | 约束 |
|---|---|
| 人力 | ≤ 1 人，且不占用 `P1-01`/`P1-02` 的关键路径人力 |
| 时间 | 路线 A：2 周；路线 B：4 周；在线评估：4 周。总计 ≤ 10 周 |
| 产品面 | 在 G2 通过前，**不新增任何用户可见的界面**——复用 `P1-02` 的建议渠道 |
| 承诺 | 对内对外均不作为交付承诺（计划 §6 明确） |

「不新增用户可见界面」这条约束很重要：它保证了 No-Go 时的退出成本接近于零，不会因为"界面都做了"而产生继续投入的沉没成本压力。

---

## 7. 风险

| 风险 | 对策 |
|---|---|
| 研究无限期延续，持续消耗资源 | §5 三道决策门 + §6 时间上限，到点必须给结论 |
| 为了指标好看而放宽"值得沉淀"的判定 | 人工判定由产品而非研发执行；在线采纳率是最终判据，无法被自我说服 |
| 挖掘结果泄露跨用户信息 | 严格单用户范围内挖掘，不做跨用户模式学习（Phase 3 才考虑，且需独立的隐私评估） |
| 因研究结论乐观而在 Phase 2 提前承诺 | 本文性质说明（§0）与 §6 承诺约束，写入 Phase 2 里程碑评审 |
