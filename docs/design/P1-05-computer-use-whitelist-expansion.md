## 1. 背景与目标

计划在两处提到这件事，措辞都很克制：

- §4.5：「扩展 Computer Use 应用白名单范围（超出 Phase 1 的 3-5 个应用）也放在这一阶段，**视 Phase 1 验收结果决定扩展节奏**」
- §9：优先级 ★★，「Phase 2，视 Phase 1 稳定性验收结果决定」

所以本文的主体**不是「怎么多接几个应用」，而是「凭什么决定接、接多少、什么标准才算接好」**。把扩展变成一条有门禁的流水线，而不是一个不断膨胀的适配清单——否则 §2.3 预警的维护成本会在 Phase 2 集中爆发。

目标：

- **G1** 明确扩展的 Go/No-Go 判据，避免在 Phase 1 尚未稳定时盲目扩张。
- **G2** 把 AppAdapter 从「内部实现」升级为「有 SDK、有门禁、有维护契约」的可复制单元。
- **G3** 建立适配器失效的**主动发现**机制，而不是等用户投诉。

非目标：

- 不做通用的「操作任意本地应用」（计划明确放在 Phase 3）。
- 不做第三方开发者提交适配器（Phase 3 Marketplace）。

## 2. 扩展前置门禁（G1，本文最重要的部分）

**在 Phase 1 的三个适配器同时满足以下条件之前，不启动任何新适配器开发：**

| 判据 | 阈值 | 数据来源 |
|---|---|---|
| golden set 成功率 | 三个适配器均 ≥ 90%，连续 4 周稳定 | `P0-08` §8.3 回归报告 |
| 真实环境成功率 | ≥ 85%（真实用户执行，含各种脏环境） | 线上遥测（`P0-08` §10） |
| L3 兜底使用率 | ≤ 10% | 线上遥测 |
| 授权率 | `desktop:*:automate` 开启率 ≥ 30% | `P0-07` §11 判定基线 |
| 维护成本 | 单适配器月均修复工时 ≤ 2 人日 | 工程记录 |
| 用户需求信号 | 有明确的、被多次提出的应用需求 | 见 §3 |

**任一不达标 → 不扩展，先修 Phase 1。** 这条要作为 Phase 2 排期的硬约束写进里程碑评审，而不是"参考指标"。

理由很直接：适配器的维护成本是累加的、持续的。在三个还没稳住的时候加到六个，只会让每个都更不稳。计划把这一项定为 ★★ 而不是更高，本身就表达了这个判断。

## 3. 候选应用评估框架（G1）

不按「感觉重要」排序，按四维打分：

| 维度 | 权重 | 说明 |
|---|---|---|
| **需求强度** | 35% | 有多少用户明确要求；能解决多高频的任务 |
| **L1 可行性** | 30% | 是否有稳定的原生 API（COM/AppleScript/官方 SDK）。**无 L1 路径的应用一律降级评估** |
| **维护风险** | 20% | 更新频率、UI 变动历史、版本碎片化程度 |
| **权限侵入性** | 15% | 需要什么系统权限；数据敏感度 |

候选池与初步判断（待真实需求数据校准）：

| 应用 | 需求 | L1 可行性 | 维护风险 | 侵入性 | 初判 |
|---|---|---|---|---|---|
| PowerPoint | 中高 | 高（COM / AppleScript） | 低 | 低 | **优先候选** |
| Word | 中 | 高（COM / AppleScript / python-docx） | 低 | 低 | **优先候选** |
| 本地文件管理器 | 高 | 高（直接用文件系统 API，无需 UI 自动化） | 极低 | 中 | **优先候选，成本最低** |
| 飞书/企微 桌面端 | 中高 | 中（有开放 API，但桌面端本身无自动化接口） | 中 | 中 | 建议走 API/MCP 而非桌面适配 |
| WPS | 中（国内） | 低（API 不完整） | 高 | 低 | 暂缓 |
| Photoshop 等专业软件 | 低 | 中 | 高 | 低 | 不做 |
| 微信桌面端 | 高 | **无**（无 API，且自动化违反其条款） | 极高 | 高 | **明确不做** |

两条从上表得出的原则：

1. **「有 API 的就别做桌面适配」**——飞书/企微这类有开放 API 的应用，应该走 MCP 连接器（`P0-05`），而不是去操作它的桌面客户端。桌面适配只用于「除了操作 UI 别无他法」的场景。
2. **文件管理类需求优先**——很多"操作本地应用"的诉求实质是"处理本地文件"，直接用文件系统 API 就能满足，稳定性远高于任何 UI 自动化。这类需求应该被识别出来单独满足，而不是包装成一个适配器。

## 4. AppAdapter SDK 化（G2）

把 `P0-08` §5 的抽象接口固化为可复制的开发单元：

```text
adapters/
├── _sdk/
│   ├── base.py              # AppAdapter 基类
│   ├── layers.py            # L1/L2/L3 降级框架
│   ├── verification.py      # 结果校验框架（P0-08 §8.2）
│   ├── snapshot.py          # 快照与回滚框架
│   └── testing.py           # golden set 运行器
├── excel/
│   ├── adapter.py
│   ├── actions.yaml         # ActionSpec 声明（含 reversible 标记）
│   ├── scope.yaml           # Scope 元数据（P0-07 §3 四段式）
│   └── golden/              # ≥25 个用例
└── <new_app>/               # 复制模板即可开始
```

**新适配器的准入清单**（缺一不可，作为合入检查）：

| 项 | 要求 |
|---|---|
| ActionSpec 声明 | 每个动作标注 `reversible`、所需 L 层、超时 |
| 结果校验 | 每个 write 动作实现执行后读回校验 |
| 快照/回滚 | 可回滚动作实现 `snapshot()` / `rollback()` |
| Scope 元数据 | 四段式说明文案（会做/不会做/留下什么/不开启也可以） |
| golden set | ≥25 用例，覆盖常规 60% / 边界 25% / 异常 15% |
| 环境矩阵 | 至少 2 个应用版本 × 目标 OS 版本 |
| 成功率 | ≥ 90%，L3 使用率 ≤ 10% |
| 遥测 | `context_shape` 定义（脱敏，见 `P0-08` §10） |

**准入不通过 → 该适配器不进入发布白名单**，但不阻塞其他适配器发版（沿用 `P0-08` §8.3 的按适配器粒度门禁）。

## 5. 适配器失效的主动发现（G3）

适配器最大的运维痛点是**静默失效**：目标应用某次更新改了控件结构，成功率悄悄从 95% 掉到 40%，直到用户投诉才发现。

三道防线：

```text
① 应用版本监控
   遥测中的 app_version 出现新值 → 自动在该版本上跑一次 golden set
   失败 → 告警 + 在客户端对该版本用户标注"该版本兼容性验证中"

② UI 结构指纹
   P0-08 §10 的 ui_tree_hash 分布突变 → 预警
   （用户还没失败，但界面已经变了）

③ 成功率滑动窗口
   单适配器 7 日成功率环比下降 > 10pp → 告警
   下降到 < 80% → 自动降级：暂停该适配器并提示用户"这个功能暂时不可用，我们在修"
```

**自动降级比让用户反复失败更好**：一个成功率 50% 的自动化功能，体验比"暂时不可用"糟糕得多，且会持续消耗用户对整个产品的信任。

降级的告知文案要具体：「Excel 更新到 16.90 后有些操作我还没适配好，正在修。你可以先上传文件让我处理。」——给出降级路径，与 `P0-07` 的 `degraded_behavior` 一致。

## 6. 扩展节奏建议

| 阶段 | 内容 | 条件 |
|---|---|---|
| Phase 2 前期 | **不扩展**，专注把 Phase 1 三个适配器做到门禁标准 | — |
| Phase 2 中期 | SDK 化 + 主动发现机制 + 文件管理能力 | §2 门禁全部达标 |
| Phase 2 后期 | 新增 1–2 个适配器（按 §3 打分选） | SDK 与监控就绪 |
| Phase 3 | 视情况扩展至通用支持（计划 §6 Phase 3） | 需重新评估，不在本文范围 |

**一次只加一个适配器，稳定 4 周后再加下一个。** 并行开发多个适配器会让失效归因变困难，也会让缓冲预留失效。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 为了"看起来能力更强"而在门禁未达标时扩展 | 极高 | §2 门禁写进 Phase 2 里程碑评审，需数据佐证方可放行 |
| 维护成本随适配器数量线性增长，吞掉 Phase 2 产能 | 高 | 每个适配器的月均维护工时纳入门禁；超过 2 人日/月的适配器触发"是否下线"评审 |
| 选了没有 L1 路径的应用 | 高 | §3 中 L1 可行性权重 30%，无 L1 路径直接降级评估 |
| 用户预期被"白名单"限制伤害 | 中 | 产品内明确展示已支持应用清单与「申请支持」入口；不承诺"能操作任何应用" |
| 与 MCP 路径重复建设 | 中 | §3 原则 1：有开放 API 的应用走 MCP，不做桌面适配 |

## 8. 验收标准

1. §2 的六项门禁指标全部可自动统计，并在内部看板可见。
2. SDK 模板可用：从复制模板到跑通第一个动作 ≤ 1 天。
3. 新适配器准入清单（§4）作为 CI 检查项，缺项阻塞合入。
4. 主动发现三道防线全部上线，用一次真实的应用版本更新验证告警链路。
5. 自动降级：模拟成功率跌破 80%，验证适配器被暂停且用户看到带降级路径的说明。
