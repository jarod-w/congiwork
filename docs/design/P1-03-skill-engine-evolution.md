## 1. 背景与目标

架构图（§3）把 Skill Engine 整体标为 P1。`P0-06` 已交付了「能创建、能执行」的最小闭环，本文覆盖把它从「能用」推向「越用越好」的部分——这正是计划 §11 第二条壁垒「Skill 资产」的实质内容。

核心判断：**Skill 的价值不在数量，在于它是否比用户每次重新描述更省事。** 因此本模块围绕一个问题设计：如何让 Skill 的成功率随使用而提高，而不是随外部环境变化而衰减。

目标：

- **G1** Skill 质量可度量、可归因到具体步骤。
- **G2** Skill 能在失败中自我修复，而不是静默失效。
- **G3** Skill 变更有版本、可回滚、可灰度。

非目标：

- 不做跨用户 Skill 共享与市场（Phase 3）。
- 不做 Skill 的分支/循环/并行控制流（保持线性，见 §6）。

## 3. 步骤级质量度量（SE-1）

```sql
CREATE TABLE skill_step_metric (
  skill_id      uuid NOT NULL,
  skill_version int NOT NULL,
  step_id       text NOT NULL,
  window_date   date NOT NULL,
  run_count     int NOT NULL DEFAULT 0,
  success_count int NOT NULL DEFAULT 0,
  fallback_count int NOT NULL DEFAULT 0,   -- 触发自愈的次数
  edit_count    int NOT NULL DEFAULT 0,    -- 用户在审批时修改的次数
  p50_ms        int NULL,
  p95_ms        int NULL,
  error_classes jsonb NOT NULL DEFAULT '{}',  -- {"tool_failed": 3, "invalid_input": 1}
  PRIMARY KEY (skill_id, skill_version, step_id, window_date)
);
```

`edit_count` 是最有价值的信号——用户在审批时修改某一步的输出，说明这一步的 instruction 不够准确。它直接驱动 SE-4。

Library 中的展示：

```text
季度渠道复盘                    运行 12 次 · 成功 10 次 (83%)
  ⚠ 步骤 2「按渠道汇总」        你有 5 次都改了输出格式  [看看怎么改进]
  ⚠ 步骤 4「发到 Slack」        近 3 次有 2 次失败       [查看原因]
```

## 4. 失败自愈（SE-3）

Skill 失效的最常见原因不是逻辑错，是**外部环境变了**：字段改名、频道改名、页面改版。硬失败对用户很挫败，且用户往往不知道怎么修。

```text
步骤 S 执行失败
   │
   ▼ 判断是否可自愈：
   │    可自愈：tool_failed / invalid_input（环境类）
   │    不可自愈：permission_denied（走授权引导）/ irreversible 步骤（绝不自动重试）
   │
   ▼ 降级为自由执行：
   │    把该步骤的 title + 上下文交给 Runtime 自由发挥（不受 Skill 约束）
   │    LLM 可自行选择其他工具/参数达成同一目标
   │
   ├── 自由执行成功
   │      ▼ 记录差异：Skill 原定 A，实际做了 B
   │      ▼ 任务结束后建议："这一步的做法好像变了，要更新技能吗？"[看看差异][更新][不用]
   │
   └── 自由执行也失败
          ▼ 作为步骤失败上报，Skill 标记为 degraded，在 Library 中标红
```

**约束**：自愈只在该步骤的 `required_scopes` 范围内进行——自由执行不得使用未授权的工具，也不得把 `write` 步骤升级为 `irreversible` 操作。这条要在 Runtime 层强制。

自愈次数上限：单次执行最多 2 步触发自愈，超过则整体失败。防止一个失效的 Skill 变成漫无目的的自由探索。

## 5. 反向优化（SE-4）

```text
触发条件：某步骤的 edit_count / run_count > 0.4 且 run_count ≥ 5
   │
   ▼ 收集该步骤的历次用户修改（diff）
   ▼ LLM 归纳共同模式："用户总是把表格改成按渠道排序"
   ▼ 生成 instruction 修订建议
   ▼ 在 Library 中提示用户：
   │    "这一步你改了 5 次，都是把结果按渠道排序。
   │     要不要我以后默认就这么做？"  [好] [不用] [我自己改]
   ▼ 接受 → skill version + 1，记 change_note
```

同时把归纳出的模式作为 **Preference Memory 候选**（`P0-02`）——如果用户在多个 Skill 里都要求按某种方式排序，那是一个跨 Skill 的偏好，不该只固化在单个 Skill 里。

## 6. Skill 推荐（SE-5）

`P0-06` §4.1 已有 keyword trigger 的推荐。本模块升级为语义匹配：

```text
用户输入任务描述
   │
   ▼ 向量检索 skill.description（复用 pgvector）
   ▼ + keyword 规则匹配
   ▼ + 上下文信号（时间：季度末；最近打开的文件类型）
   │
   ▼ 综合打分，top-1 超过阈值才推荐（宁缺毋滥）
   ▼ 展示："看起来像「季度渠道复盘」，用这个吗？"[使用][不用][别再问了]
```

仍然**只推荐不自动执行**，与 `P0-06` 保持一致。理由未变：自动执行在 Skill 质量尚未被用户充分信任时会造成失控感。是否放开到自动执行，应作为 Phase 3 的独立决策，前提是 Skill 成功率数据足够好。

### 6.1 关于控制流的取舍

有人会提出 Skill 需要条件分支（「如果数据缺失就跳过分析」）。**Phase 2 明确不加。**

理由：分支一旦引入，Skill 就从「用户能看懂的步骤清单」变成「用户需要理解的程序」，编辑器复杂度和用户认知成本都会跳一个台阶。而 §4 的失败自愈机制已经覆盖了大部分需要分支的场景——环境异常时 LLM 自由处理，比预先写死的分支更灵活。

若真实数据显示大量 Skill 因缺少分支而失败，再作为 Phase 3 议题重新评估。

## 7. 回归评测（SE-6）

Skill 变更（用户编辑、SE-4 自动优化、SE-3 建议更新）后需要验证没变坏：

```text
变更提交
   │
   ▼ 静态校验：schema、工具存在性、Scope 推导一致性
   ▼ dry-run：用最近一次成功执行的参数跑一遍试运行
   │    比对：步骤序列是否合理、所需权限是否变化、预计产物形态是否一致
   ▼ 权限升级检查：新版本若需要更高 risk 的 Scope → 强制用户重新确认
   ▼ 通过 → 生效；不通过 → 提示并保留旧版本
```

**权限升级检查是硬性的**：Skill 编辑不能成为绕过授权的路径。任何使 `required_scopes` 扩大或 risk 升级的变更，都必须走一次显式确认。

灰度（SE-2）：新版本先执行 3 次，若成功率低于旧版本，提示用户「新版本好像不太行，要回滚吗」。样本量小，只做提示不自动回滚。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 自愈掩盖了真实问题，Skill 逐渐名存实亡 | 中 | `fallback_count` 单独统计并在 Library 显式展示；连续 3 次自愈必定提示用户更新 |
| 自愈时 LLM 自由执行造成预期外副作用 | 高 | §4 的 Scope 与 risk 约束；`irreversible` 步骤永不自愈；自愈产生的动作仍走审批 |
| 反向优化把偶然行为固化成规则 | 中 | 阈值门槛（>40% 且 ≥5 次）；建议而非自动应用；展示具体的历次修改证据 |
| 推荐不准造成干扰 | 中 | 高阈值，宁缺毋滥；「别再问了」按 Skill 记忆 |
| 度量数据不足（Skill 使用频次低） | 中 | 阈值基于绝对次数而非仅比例；数据不足时不展示成功率，展示「运行次数太少，还看不出来」 |

## 9. 验收标准

1. 步骤级指标可在 Library 中查看，且能定位到具体失败步骤与失败分类。
2. 构造一个工具失效场景，验证自愈触发、任务仍完成、且产生更新建议。
3. 验证 `irreversible` 步骤失败时不触发自愈。
4. 验证 Skill 编辑导致 `required_scopes` 扩大时，强制重新确认（自动化测试）。
5. 反向优化建议的接受率 ≥ 40%（低于此说明归纳质量不足）。
6. 推荐的采纳率 ≥ 30%，「别再问了」触发率 ≤ 10%。

## 11. 待决问题

1. Skill 数量增长后（单用户 >30 个），Library 是否需要分类/文件夹？倾向先用标签 + 搜索，不做层级目录。
2. 自愈产生的「差异」若用户从不确认更新，是否应在 N 次后自动更新？倾向不自动——静默改变用户的 Skill 违背可控原则。但需观察实际的确认率。
